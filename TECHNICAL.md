# C13PowerDashboard — технічна документація

Детальний опис для розробника або AI-асистента, який бачить проєкт уперше. Користувацький огляд — у `README.md`, короткий вступ для вставлення в новий чат — у `AI-CONTEXT.md`.

Жодних секретів у цьому файлі немає. Значення App ID, App Secret, логіна й пароля Deye зберігаються лише там, де вказано в розділі «Секрети».

## 1. Що це і як влаштовано

Дашборд «Чавдар 13» показує мешканцям будинку три речі: чи є мережа на вході інвертора, чи працює інвертор (схема з АВР, пріоритет у мережі), заряд і режим батареї. Додатково — приблизний час, коли мережа з’явилася або зникла (з історії Deye Cloud).

```
Deye Cloud (EU API)  →  Cloudflare Worker `c13-power`  →  статична сторінка (GitHub Pages)
                          /api/status, кеш 30 с           браузер мешканця
```

- Сторінка — чистий HTML/CSS/JS без збирача й залежностей: `public/`.
- Worker — `worker/index.mjs` + `lib/*.mjs`. Єдине місце, де є паролі Deye. Браузер ніколи не звертається до Deye напряму.
- Адреси:
  - сторінка: `https://sergeymaximenko.github.io/C13PowerDashboard/`
  - Worker: `https://c13-power.sergeymaximenko.workers.dev` (дані: `/api/status`, перевірка: `/` або `/health` → `{"ok":true}`)
- Репозиторій: `https://github.com/SergeyMaximenko/C13PowerDashboard`, гілка `main`. Локальна копія: `C:\Users\maximenko\Documents\GitHub\C13PowerDashboard`.
- Автоматичного оновлення сторінки немає: дані беруться при відкритті, натисканні кнопки «Оновити» (cooldown 10 с) і при поверненні у вкладку, якщо минула більше 60 с.

1. Правки у файлах.
2. `npm test` — усе зелене.
3. Якщо змінювалось що-небудь у `worker/`, `lib/` або `wrangler.toml` → `npx wrangler deploy`. **Push у GitHub Worker не оновлює.**

Правки лише в `public/` (сторінка) не потребують `wrangler deploy`. Правки лише в `worker/` і `lib/` не потребують push для роботи Worker, але їх усе одно треба закомітити.

## 6. Worker

### 6.1. Маршрути (`worker/index.mjs`)

- `GET /` і `GET /health` → `200 {"ok":true}` (без звернення до Deye).
- `GET /api/status[?station=ID]` → показники.
- `GET /api/generator?from=РРРР-ММ-ДД&to=РРРР-ММ-ДД[&station=ID]` → робота генератора за період (див. 6.6). Основна сторінка його не викликає.
- `OPTIONS` → `204` з CORS-заголовками.
- інші методи/шляхи → `404` або відмова. Для станції не зі списку → `403`.

Заголовки відповіді: `Cache-Control: no-store`, `Access-Control-Allow-Origin` (`*` або `ALLOWED_ORIGIN`), `X-Content-Type-Options: nosniff`, `X-Cache: HIT|MISS|STALE`, `X-Cache-Age: <с>`.

### 6.2. Кеш і стан

- Модульна змінна `entries` (Map за `stationId`) живе, поки тепла ізоляція Worker. Для кожної станції: `cache` (остання відповідь + час), `shared` (`token`, `expiresAt`, `historyCache`). Максимум 10 станцій.
- Відповідь кешується на `CACHE_SECONDS` (120 с): у пам'яті ізолята (`X-Cache: HIT`) і в Cloudflare Cache API дата-центру (`X-Cache: EDGE`), яке спільне для всіх ізолятів. Протягом цього часу звернення до Deye немає. Список інверторів кешується на 24 год.
- Якщо Deye повертає помилку, а старий кеш існує — віддається він із `X-Cache: STALE`.
- **Правило:** між запитами зберігаються лише прості дані (токен, масиви, Map). **Ніколи не зберігати й не очікувати `Promise`, створений іншим запитом**: у Cloudflare Workers це підвішує запит («signal timed out»). Кожен запит створює власний `DeyeClient`, який отримує `shared` лише як сховище даних.
- `Date.now()` у Workers не просувається під час синхронної роботи CPU; на це не слід спиратись для вимірювання.

### 6.3. Deye клієнт (`lib/deye.mjs`)

- Токен кешується до `expiresAt − 60 с`.
- Для станції викликаються: `station/latest`, `station/device` (список інверторів), `device/latest` (показники, пачками по 10 пристроїв), а для історії `device/history`-подібні запити через `historyDay`.
- Історія: показники за сьогодні перезавантажуються лише коли змінився `collectedAt` (час вимірювання інвертора); завершений попередній день кешується один раз (`complete`). Кеш історії — до 12 записів. Це головна оптимізація CPU.
- Логер Deye передає дані в хмару раз на ~5 хв; Worker цю затримку не змінює.
- Список інверторів (`station/device`) кешується на 24 год у `shared.devices` (`deviceList()`), тому більше не запитується при кожному оновленні.
- Відомий резерв оптимізації: пауза після помилки Deye (щоб відвідувачі не штурмували API при збої).

### 6.4. Що віддається браузеру

`lib/public-status.mjs` пропускає лише дозволені поля (allowlist), зокрема: `station.name`, `collectedAt`, `grid`, `output`, `soc`, `batteryMode`, `loadWatts`, `allPhasesZero`, `events` (appeared/disappeared), `historyError`, `historyAvailable`, `diagnostics` (числові таймінги, `runId`/`runAttempt` — на них спираються тести). Секрети, токени, паролі та сирі відповіді Deye виходити не повинні — це перевіряє `tests/worker.test.mjs` (рядок `LEAK`).

### 6.5. Обмеження Cloudflare (безкоштовний план)

100 тис. запитів/добу, 10 мс CPU на виклик, 50 підзапитів. Фактично: ~1,2 тис. викликів/добу, помилок 0; P50 ≈ 6 мс, P90 ≈ 24 мс, P99 ≈ 32 мс (запити без кешу). Перевищення CPU дає помилки 1102 лише для окремих запитів, а не блокування акаунта. Метрики: Workers & Pages → `c13-power` → Metrics / Errors.

### 6.6. Облік роботи генератора (`/api/generator`, `lib/generator.mjs`)

- Запит: `from`, `to` (дні за Києвом, `to` не в майбутньому, не більше 31 дня; без `from` береться 7 днів). Помилка параметрів → `400`.
- Джерело: `device/history` (`granularity=1`, точки раз на ~5 хв) за кожен день. У `measurePoints` лише 4 ключі: `GenVoltageL1–3`, `TotalGeneratorPower`. **Більше ключів Deye відхиляє** (`list too long`, код `2101007`).
- Стан точки визначає `generatorInfo()` (напруга GEN ≥ 150 В або потужність ≥ 800 Вт = працює). Точки без показників генератора пропускаються.
- Сеанс: послідовні точки «працює». Закінчується на першій точці «зупинений» (час цієї точки), а при прогалині в даних > 20 хв — на останній точці «працює». Точність ±5 хв (межі між вимірюваннями, не секундомір). Тільки сьогоднішній сеанс може бути `open: true` (кінця ще немає).
- День рахується окремо (хвилини, `starts`, `peakW`). Сеанс через північ у `sessions` склеюється (`mergeAcrossMidnight`, за прапором `cut` — сеанс обірвався кінцем даних, а не точкою «зупинений»); у `days[]` хвилини лишаються по календарних днях.
- Зберігання: завершені дні не змінюються, тому рахуються один раз: пам'ять ізолята + KV (binding `GEN`, ключ `gen:v2:<stationId>:<дата>`, значення — JSON підсумку ≈ 300 байт). Без KV усе працює, але дні перераховуються після перезапуску. Сьогодні перераховується не частіше ніж раз на `GENERATOR_TODAY_SECONDS` (600 с). Дні без даних Deye не записуються в KV (`missingDays: no-data`). Якщо змінюється формат підсумку, треба підняти версію в ключі (`v2` → `v3`).
- Захист квоти Deye: не більше 7 нових завершених днів за один запит (≈3 виклики на день, 50 підзапитів на запит у безкоштовному плані); решта в `missingDays` з `reason: "pending"` — повторити запит. Сьогодні в ліміт не входить. Помилка одного дня (`reason: "error"`, `message`) не ламає відповідь.
- Відповідь: `{ from, to, timezone, totalMinutes, totalStarts, sessions[{start,end,minutes,peakW,open,startLocal,endLocal}], days[{date,minutes,starts,peakW}], missingDays[{date,reason,message?}] }`.
- Тести: `tests/generator.test.mjs`.
- Пароль звіту: ендпоінти `/api/generator` і `/api/generator-report` (імена тих, хто заправляв) захищені секретом `REPORT_PASSWORD` (`npx wrangler secret put REPORT_PASSWORD`; локально — у `.dev.vars`). Сторінка надсилає його в заголовку `X-Report-Password` (URL-кодований, тому підходять будь-які символи), запам'ятовує в `localStorage` лише після успішної відповіді й забуває при `401`. Без секрету звіт відкритий. `/api/status` пароля не вимагає. Невдалі спроби: 10 за 10 хв з однієї адреси (`CF-Connecting-IP`, у межах ізолята), далі `429`. Порівняння пароля — без раннього виходу. Короткий пароль легко підібрати: чим довший, тим краще. Тести: `tests/auth.test.mjs`.
- Звіт із заправками: `GET /api/generator-report?from=&to=` (за замовчуванням останні 7 днів, ≤ 31). Джерело заправок — Google Sheet, опублікований як CSV; посилання лише в секреті `REFUELS_CSV_URL` (`npx wrangler secret put REFUELS_CSV_URL`), браузеру не віддається і в помилках маскується. Кеш таблиці 10 хв (`REFUELS_SECONDS`); при збої віддається остання вдала таблиця й `refuelsError`.
  - Парсер (`lib/refuels.mjs`): рядок заголовка шукається за колонкою «Дата заправки»; час заправки береться з неї (не з «Дата події»); колонки «Літри», «Режим тесту», «Не враховувати …» знаходяться за назвою. Рядки з «так» у «Режим тесту» або «Не враховувати …» та без коректного часу пропускаються. Час за Києвом, години з однією цифрою (`8:56`), кома як десятковий роздільник у літрах.
  - Відповідь: як у `/api/generator` плюс `days[].refuels[{at,atLocal,liters}]`, `refuels` (за період), `since` (`refuel`, `minutes`, `hours`, `starts`, `open`, `truncated`, `complete`), `refuelsConfigured`, `refuelsError`.
  - `since`: від моменту останньої заправки до зараз (до 120 днів назад); сеанс, що перетинає момент заправки, обрізається. Дні рахуються з тим самим ліміту 7 нових днів на запит; `since.complete: false` означає, що частину днів ще довантажують (`pending`) — запит повторити.
- Налаштування KV: `npx wrangler kv namespace create GEN`, id у `[[kv_namespaces]]` у **кінці** `wrangler.toml` (після `[vars]`, інакше наступні змінні потраплять у таблицю KV).

## 7. Бізнес-логіка (`lib/domain.mjs`, `public/app.js`)

### 7.1. Мережа на вході (`grid`)

- `on` — 180–260 В на всіх очікуваних фазах і 45–55 Гц.
- `off` — напруга < 50 В і частота < 1 Гц (`allPhasesZero`, якщо всі фази 0).
- `unstable` — повні вимірювання, але поза діапазонами.
- `unknown` — неповні дані.
- Дані старші за `STALE_MS` = 30 хвилин (`lib/domain.mjs`; у `public/app.js` дзеркальна константа `STALE_AFTER_MS`, їх треба міняти разом) → усе «невідомо» (`stale`). Позначка «Пройшло …» стає жовтою після 15 хвилин (`WARN_AFTER_MS`).

### 7.2. Батарея

- **Мережа є + малий «розряд»:** якщо мережа на вході `on`, а потужність розряду менша за 150 Вт (`MAINS_IDLE_LIMIT` у `lib/domain.mjs`), режим батареї — `idle`, а не `discharging` (це власне споживання інвертора/BMS). На плитці: при заряді ≥ 99% «Повністю заряджена», інакше «У режимі очікування». Без мережі поріг лишається 70 Вт, і розряд реальний. Зі 150 Вт і більше — «Розряджається».

- `soc` береться з вимірювання інвертора (пріоритет), інакше із зведених даних станції.
- `batteryMode`: за `BatteryPower` для одного інвертора: > 70 Вт → `discharging`, < −70 Вт → `charging`, інакше `idle`. Поріг 70 Вт задано змінною `limit` у `lib/domain.mjs` (раніше було 20 Вт; дрібні 30 Вт вважалися розрядом). Для кількох інверторів або без `BatteryPower` — резервний розрахунок зі станційних `chargePower`/`dischargePower` з тим самим порогом.

### 7.3. Стан інвертора (`inverterState` у `public/app.js`)

Схема з АВР: за наявності мережі АВР підключає будинок до неї, тому інвертор не живить мешканців.

- Мережа `on`: `charging` → «Інвертор заряджає акумулятор»; вихід `off` → «Немає напруги на виході»; `idle` або `discharging` → «Інвертор у режимі очікування» (дрібний розряд при мережі — внутрішня робота інвертора); інакше `unknown`.
- Мережа `off`: вихід `on` і навантаження > 0 → `supplying` («Будинок живиться від батареї», а коли працює генератор, «від генератора»); вихід `off` і є навантаження → `unknown`; навантаження 0 і зарядка → `charging`; вихід `off` → `off`; навантаження 0 і `idle`/`discharging` → `standby`; інакше `unknown`.
- Тести: `tests/operation.test.mjs`.

### 7.4. Час «з’явилася / зникла ≈»

Середина інтервалу між двома історичними вимірюваннями з різним станом мережі. Приблизний час; якщо перехід не знайдено або історія недоступна — рядок прихований. Для станції з кількома інверторами не показується.

### 7.5. Генератор (вхід GEN інвертора)

Генератор підключено до окремого входу GEN, тому Deye віддає його як окремі параметри в `device/latest`: `GenVoltageL1–3`, `GenPowerL1–3`, `GeneratorActivePower`, `TotalGeneratorPower` (лічильники `TotalGeneratorProduction`, `Gen…RunTime` ігноруються). Логіка в `generatorInfo()` і `summarize()` (`lib/domain.mjs`): генератор «є» (напруга ≥ 150 В або потужність ≥ 800 Вт); якщо при цьому потужність < 800 Вт і батарея ще **розряджається**, стан `starting` («Готується до роботи» / «Генератор запущено, чекаємо підключення»: двигун працює, але інвертор ще не взяв генератор після паузи стабілізації, будинок живиться від батареї); інакше `on` («Працює»); `off` («Зупинений»), якщо значення є, але напруги й потужності немає; `unknown`, якщо параметрів немає або дані застаріли. Текст «Будинок живиться від генератора» показується лише в стані `on`. Відповідь `/api/status` має поле `generator: { state, powerW, voltageV }`. На сторінці це окрема картка «02 / ГЕНЕРАТОР» (стани «Працює» / «Не працює» / «Невідомо», потужність і напруга, анімація генератора з димком і мерехтливою блискавкою) і текст «Будинок живиться від генератора» в картці інвертора, коли мережі немає (`public/app.js`, `#generator-card`). Картка з'являється, коли станція вперше повідомила дані генератора; для станцій без нього вона не показується. На широких екранах (≥1200 px) картки в один ряд по чотири, на середніх 2×2, на мобільному одна під одною. Приклад у списку «Перегляд»: «Приклад: працює генератор». Якщо генератор колись підключать через АВР на вхід мережі, поля `Gen…` лишатимуться нульовими, а інвертор бачитиме його як мережу.

## 8. Фронтенд

### 8.1. Потік даних (`public/app.js`)

`api()` формує URL (`?api=` лише localhost, інакше `<meta name="dashboard-api">`; `?station=` лише цифри), `fetch` з `cache: 'no-store'` і таймаутом 45 с. `refresh()`: показує скелетон (`setLoading`), до 3 повторів по 10 с при помилці, ігнорує відповіді з меншим `collectedAt` (монотонність), `requestVersion` проти гонок. `render(data, example)` оновлює картки. Таймери: 1 с — «Пройшло …» і тривалість стану мережі, 15 с — повторний рендер для застарівання.

### 8.2. Анімації

- Картка мережі (`#grid-anim`): при `grid === 'on'` — опора з проводами, що погойдуються, і пунктир-струм.
- Картка інвертора (`#inverter-anim`): дві великі шестерні, що обертаються в різні боки (при `supplying` і `charging`). Шестерня описана один раз у `<defs id="iv-gear-shape">` і підключається через `<use>`.
- Картка батареї: герой-акумулятор. Зарядка — щасливий, стрибає, іскри, рівень знизу вгору; розряд — сонний, рівень згори вниз і літери Z, що вилітають (контури `<path>`, не текст). Колір картки при розряді бурштиновий.
- Скелетон завантаження і «бульбашки» біля повідомлення про затримку.
- `prefers-reduced-motion` вимикає всі анімації.

### 8.3. Пастки (вже зустрінуті)

- **Стилі всередині `<use>`**: селектори на кшталт `.parent .child` не діють на елементи в shadow-дереві `<use>`. Використовувати прості класи без батьківського префікса (`.iv-fill`, не `.ivscene .iv-fill`).
- **Атрибут `hidden` на SVG** як властивість `.hidden` не працює — використовується `setHidden(el, on)` з `toggleAttribute`.
- **Глобальне правило `svg { fill:none; stroke:currentColor }`** вимагає явних `fill`/`stroke` у класах.
- **Safari (iPhone)**: анімація зі змінними CSS у `@keyframes` (`var(--lvl)`) зависала після зміни значення → використовуються окремі `@keyframes` `m-level-up`/`m-level-down`, напрям задає `data-dir`. SVG-`<text>` з трансформаціями анімувався нестабільно → літери Z намальовані контурами. Не додавати вручну перезапуск анімацій (`getAnimations().cancel()`): він погіршив стабільність.
- Пульсація скелетона не повинна накладатись на анімовані сцени (`:not(.mascot):not(.ivscene):not(.gridscene)`).
- Змінних CSS з інших дизайн-систем на сайті немає. Власні: `--muted --border --green --red --amber`, на картці `--accent`, `--tint`.
- Усі три плитки мають однакову «рамку» іконки: 104 px на ПК, 88 px до 760 px, 68 px до 350 px; на мобільному іконка по центру картки за висотою, на ПК — по центру за шириною.

### 8.4. Тести і порізка `app.js`

Тести завантажують фрагменти `public/app.js` за маркерами рядків: від `function inverterState(` до `function measurementDateLabel(`, від `function render(` до `async function api(`, до `async function refresh(` — і запускають у `vm` з імітацією DOM (прості об’єкти без `style`, `classList`, `toggleAttribute`). Тому: (а) не переставляти ці маркери; (б) нові допоміжні функції, які використовує `render`, класти між `render` і `async function api(`, а звернення до `style` робити як `style?.setProperty`; (в) нові DOM-виклики у `render` повинні переживати прості об’єкти.

## 10. Публікація сторінки (GitHub Pages)

`.github/workflows/pages.yml`: тригери — `push` у `main` і ручний запуск; кроки: checkout → Node 22 → `npm test` → `npm run build` → upload `dist` → deploy-pages. Секрети Deye не потрібні. Якщо тести падають — публікації не буде (дивитись GitHub → Actions → червоний крок). Файли `app.js` і `styles.css` у `dist/` отримують `?v=<hash>`, тож браузери підтягують нову версію.

## 11. Типові проблеми

| Симптом | Причина / дія |
|---|---|
| Сторінка: «signal timed out» | Раніше — спільний Promise між запитами в Worker (вже усунено). Перевірити, чи Worker відповідає на `/health`. |

| Після push на сторінці старий вигляд | Ще йде Actions або кеш браузера: Ctrl+F5, на iPhone — нова вкладка/приватна. |
| Worker поводиться по-старому | Забули `npx wrangler deploy`. Перевірити Deployments. |
| «Немає напруги на виході» двічі | Рядок `output-detail` приховується при `operation === 'off'`. |
| Усе «Невідомо» | Дані старші за 1 годину або логер Deye не передає. |
| Анімація зависає на iPhone | Дивитись розділ 8.3 (змінні в keyframes, `<text>`, перезапуск анімацій). |

## 12. Історія ключових рішень

1. Початково дані збирав GitHub Actions за розкладом і публікував JSON у Pages — затримки й обмеження Actions. Замінено на Cloudflare Worker із кешем 30 с.

4. R2/окремий збирач за розкладом розглядалися й відкинуті: помилок 0, навантаження мале.
5. Поріг режиму батареї піднято з 20 до 70 Вт; при наявній мережі дрібний розряд не робить стан інвертора «невідомим».
